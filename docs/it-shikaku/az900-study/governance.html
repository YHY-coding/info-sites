11. ガバナンスとコンプライアンス(タグ・ロック・Policy・RBAC)

最重要:タグ・リソースグループ・ロック・予算の役割分担

機能たとえ目的覚えるポイント
タグ荷物に貼る付箋リソースにメタデータ(キー:値)を付けて横断的に分類・集計例: 部署=営業。RGやサブスクに付けても、中のリソースに自動継承されない。継承させるにはAzure Policyで別途設定
リソースグループ引き出し/箱同じライフサイクルのリソースをまとめる粒度が粗い。部署別の細かい分類はタグ
ロック扉の南京錠削除防止/変更防止下記参照
予算家計簿アプリのアラート支出の警告だけリソースを守る/分類する機能ではない

「部門ごとに使用量や支出を分類したい」→ タグ。

リソースロック

  • 種類: CanNotDelete(削除不可。読み取り/変更は可)、ReadOnly(読み取り専用。変更も削除も不可)
  • Ownerなどの高い権限でも、ロックがあれば削除/変更できない(先にロックを外す必要がある)
  • 継承: 親(サブスクリプション/RG)に付けたロックは子に継承される。複数ある場合は最も制限の強いものが効く

Azure Policy と Azure RBAC(最重要の似た者ペア)

Azure PolicyAzure RBAC
対象リソース(モノ・場所・性質)人(ユーザー・グループ・アプリ)
質問「何を作ってよいか/どう設定すべきか」「誰が何をしてよいか」
例特定のリージョンでしかリソースを作れない、特定のVMサイズのみ許可、タグを必須にするAさんは閲覧のみ、Bさんは共同作成者
たとえ街の条例鍵の配布係

判定: 「場所・性質の制約」はPolicy、「人の権限」はRBAC。「特定のリージョンでのみリソース作成を許可」はPolicyです。「特定のユーザーだけ制限したい」はRBACです。

  • Azure Policyのイニシアチブ: 複数のポリシー定義をまとめた束(コンプライアンス目標ごとなど)
  • ポリシーは、非準拠のリソースを検出(Audit)・拒否(Deny)・自動修復などができる

Azure RBAC(ロールベースのアクセス制御)

  • スコープ: 管理グループ > サブスクリプション > リソースグループ > リソース。上位の割り当ては下位に継承される
ロール日本語できること
Owner所有者全操作+他者へのアクセス権付与
Contributor共同作成者リソースの作成・管理は全部。ただしアクセス権(ロール割り当て)の管理はできない
Reader閲覧者見るだけ
User Access Administratorユーザーアクセス管理者アクセス権の割り当てだけ
  • Azure RBAC(リソース向け)とMicrosoft Entraロール(Entra ID内部のタスク向け)は、名前が似ているが別システム
  • 「サービス管理者」はAzureの古い(レガシー)管理モデルの概念で、1サブスクリプションに1人。RBACの所有者(複数人に割り当て可能)とは別物

Azure Blueprints(開店キット)

  • コンプライアンスに準拠した環境を、何度でも同じように展開するためのパッケージ。3点セットは、ARMテンプレート+Azure Policy割り当て+RBACロール割り当て
  • 複数サブスクリプションへの展開に便利
  • 注意: Azure Blueprintsは廃止が決まっており、廃止時期は延期されることがあります。代替は、Template SpecsとDeployment Stacks(+Azure Policy)です。最新の状況は必ず公式で確認してください。問題集には今も出題されることがあるため、概念(ポリシー+RBAC+ARMテンプレートのセット)は知っておきます

ARMはすべての操作の通り道で、ロック・RBAC・Policy・タグはARMレベルで効きます。Azure Arcを使うと、Azure外のリソースにもPolicy・RBAC・タグ・監視を適用して一元管理できます。
