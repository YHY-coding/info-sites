1. ID・ガバナンス(会社の入館証・セキュリティシステム)

権限カードには2種類あると最初に押さえると、見慣れない役職名が出ても迷いません。

  • 会社全体の入退館システム = Microsoft Entra ID(旧Azure AD)
  • 社員証を持つ本人 = ユーザーアカウント
  • 会社が管理するビル = サブスクリプション
  • ビルの中のフロア = リソースグループ
  • フロアの中の部屋・設備 = VMやストレージなどのリソース

権限カードは2種類ある(最重要)

Azure RBACEntraディレクトリロール
たとえ建物側の鍵総務部・人事部のスタッフ証
管理する対象Azureリソース(VM・ストレージ・ネットワーク)社員アカウント・グループ・デバイス
代表例所有者、共同作成者、閲覧者、ユーザーアクセス管理者全体管理者、ユーザー管理者

2つは別々のシステムで、既定では互いにまたがりません。見慣れない「〇〇管理者」が出たら、まず「リソースの操作権限か、入退館システム自体の管理権限か」を判定します。

ロール名は、後ろの役職部分が権限の強さを決める

サービス名が合っていても、役職の部分が弱ければ目的は達成できません。たとえば「〇〇のオペレーター」は、すでにあるものの読み取り・有効化・無効化までで、作成・更新には「〇〇の共同作成者」や「共同作成者」が必要です。

日常のたとえ
建物側の鍵のカードには肩書きが書いてあります。「オペレーター」のカードは、すでに設置された設備のスイッチを入り切りして中を見る係です。新しく設備を設置する係は「共同作成者」のカードです。

カスタムロールのJSON

会社独自のオーダーメイドカードを自作する仕組みです。

項目意味
assignableScopesこのカードを配ってよい範囲(どのビル・フロアの社員に配るか)
actions管理操作としてできることのリスト
notActionsactionsからの除外。絶対的な拒否ではなく、他のカードで許可されていれば操作できる
dataActions / notDataActions設備の管理ではなく、設備の中身のデータそのものを触る権限

グループとライセンス

  • 手動グループは、名簿係が手作業でメンバーを出し入れする名簿
  • 動的グループは、属性の条件ルールでAzureが自動でメンバーを出し入れする名簿。所有者や管理者ロールを持っていても、手動でメンバーを追加できない
  • 動的グループの規則は、InとnotInなどの否定語を一文字も見落とさず読む。否定語の有無だけで答えが正反対になる
  • グループベースライセンスは、入れ子になった子グループのメンバーには及ばない。直接のメンバーにだけ届く(個人に直接付けたライセンスは、グループとは無関係に有効)
日常のたとえ
入館許可を名簿Group1に付けると、Group1に直接名前が載っている人にだけ配られます。名簿の中に別の名簿が入っていても、その中の人には配られません。

一括操作と外部ゲスト

  • Entraのユーザー一括削除では、CSVに書く属性はユーザープリンシパル名(UPN)のみ。表示名は同姓同名がありうるため、特定に使えない
  • 自社が所有しないドメインのメールアドレスの人は、通常の「新しいユーザーを作成」では登録できない。専用の「外部ユーザーの招待」からゲストとして招待する(Microsoft Entra B2Bコラボレーション)
  • 招待がエラーになったら「外部コラボレーションの設定」(誰が招待できるか、どのドメインを許可・拒否するか)を確認する
日常のたとえ
UPNは「建物名+部屋番号」の宛名で、建物全体で必ず1つです。表札(表示名)は同じ名前が複数ありえます。

認証方式(ハイブリッド)

社員の本人確認を、本社(Azure)と支社(オンプレAD)のどちらが担当するかの違いです。

方式動きAzureにパスワードやハッシュが残るか
パスワードハッシュ同期本社が合言葉の暗号化コピーを保管して自分で照合する残る
パススルー認証本社は持たず、その場で支社にリアルタイムで問い合わせる残らない
AD FS(フェデレーション)本社は確認せず、支社の専門受付に転送する残らない

「パスワードやハッシュを一切Azureに保存したくない」という要件なら、パススルー認証かAD FSが正解です。

条件付きアクセス・Identity Protection・PIM

  • 条件付きアクセス = 受付の入館ルールブック(IF-THENの条件を、サインインのたびにチェック)
  • Identity Protection = 受付の不審者検知センサー(リスクを自動検知して、条件付きアクセスに情報を渡す)
  • PIM = 強力な万能鍵は普段は金庫にしまい、必要なときだけ一時的に有効化する仕組み

Azure Policy

  • RBACは「人」への許可、Azure Policyは「会社全体の内規」。別のレイヤー
  • 「許可されていないリソースの種類」に指定された種類は、所有者であっても、そのスコープに新規作成できない
  • ポリシーが上位階層に割り当てられると、配下の全階層が除外の候補になる
  • 対処は権限をいじることではなく、ポリシー自体(禁止リスト)を編集すること
  • ディレクトリレベルとは、Entraテナント全体を指す、サブスクリプションより上の階層
